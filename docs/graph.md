# Task graph engine (Phase 1)

[Docs index](index.md) · [Build](build.md) · [Diagnostics](diagnostics.md) · [JSON protocol](json-protocol.md)

*ccb-graph*

CCB executes builds as a task graph (DAG), not a hardcoded stage
list. Each pipeline stage is a task with an explicit ID, type,
declared inputs and outputs, dependencies, execution state, and
cache policy. The graph engine (`src/ccb_graph.{h,c}`) validates the
graph, computes the execution order, and runs it; the pipeline
(`src/ccb_pipeline_graph.{h,c}`) builds one task per stage from the
loaded config. Stage bodies are unchanged — the graph only decides
the order tasks run in.

## Task model

*ccb-graph-task*

| Field | Meaning |
| ----- | ------- |
| ID | Stable, unique within the graph; used in diagnostics and the build summary. Stage tasks use the stage name (`deps`, `compile-code`, `dexcheck`, …). |
| Type | Provider/kind (`aapt2`, `kotlin`, `dex`, `manifest`, …). |
| Inputs | Logical names. `SOURCE` inputs are project files (config paths); `GENERATED` inputs are produced by another task in the graph; `ENV` inputs are environment variables read by name only (the value is never recorded, so a signing password variable is declared without leaking the secret). Each input is required or optional: a missing required `SOURCE` input is CCB-E1015 under `ccb_graph_check_source_inputs`; an optional one may be absent. Every pipeline `SOURCE` input is required (see below). |
| Outputs | Logical names other tasks consume (`linked-apk`, `r-java`, `classes`, `dex`, …). Two tasks may not claim the same output. |
| Dependencies | Task IDs that must finish first. The pipeline graph chains each stage after the previous one, so the order is exactly the legacy stage order — except modules (below), which fan out as siblings and join at `merge-manifest`. |
| State | `WAITING → READY → RUNNING → DONE`, plus `FAILED` and `CANCELLED` (see below). |
| Cache policy | `FINGERPRINT` (may skip on unchanged inputs) or `ALWAYS_RUN` (runs every build; `dexcheck`). |
| Skip reason | When a task skips, the executor records why (`skip_reason`): the reason of the cache event the step logged during its own run (e.g. `source inputs unchanged`, `no sources to compile`). A skip that logs no reason reports `null`. The reason appears on the task's `finished` event and in the `build_done` `tasks[]` summary. Cache *miss* reasons are not recorded yet: no step logs why a fingerprint differed, so there is nothing to carry — that is Phase 3 cache work. |
| Run function | The existing stage function behind a thin wrapper. `config` has no run function: stage 0 is the bootstrap that loads the project model, so the driver marks it `DONE` with stage 0's duration before execution. |

Inter-task artifacts use shared logical names, not file paths:
`project-model` and `toolchain` (config → every task),
`aar-extracted`, `library-aars`, `merged-manifest`,
`compiled-res`, `linked-apk`, `r-java`, `classes`, `dex`,
`native-libs`, `unsigned-artifact`, `aligned-artifact`,
`signed-artifact`. Module AARs use one name per module,
`module-aar-<name>` (Step 8: one task per module, below), not one
shared `module-aars`. A task with no outputs (`dexcheck`,
`verify`) is a check, not a producer.

## What the builder declares per task

*ccb-graph-builder-inputs*

The builder declares an input on the task that reads it, not on
the graph as a whole:

- `config` reads the config file at its real discovered path and
  the manifest (stage 0 verifies the manifest package matches
  `project.package`), and produces `project-model` and `toolchain`.
- Every other task consumes `project-model` and `toolchain` (stage
  0 resolves the SDK, and every step invokes at least one resolved
  tool), so a config or toolchain change invalidates the whole
  graph in affected-task terms.
- `compile-code` declares the classpath jars and the compiler
  plugin jars; `dex` declares the same jars plus the ProGuard
  rules file when release minification is on.
- `native` declares the NDK sources only with `[ndk]` and
  `CMakeLists.txt` only with `[cmake]` — without those sections
  the step reads neither.
- `sign` declares the keystore file and, for release builds, the
  two password variables as `ENV` inputs (names only). The one
  deliberate gap: the default debug keystore
  (`~/.android/debug.keystore`) is generated by the step when
  absent, so it is not a declared input — it is an output of the
  step as much as an input.
- Modules (Step 8) are one task per module, not one `modules`
  task: task `module-<name>`, type `module`, output
  `module-aar-<name>`, source input the module dir. Each depends
  on `deps` + `libraries` (its classpath needs the declared and
  library AAR classes) and on its own upstream modules
  (`module-<dep>` per `depends` entry), so independent modules
  fan out and a module rebuilds only when its own inputs or an
  upstream module changes. `merge-manifest` declares every
  `module-aar-<name>` as a GENERATED input and depends on every
  module task (the fan-in join); `compile-res`, `compile-code`,
  and `dex` declare the per-module AARs too and reach them
  transitively through the chain. With no modules there is no
  module task at all, and the plan has one fewer task than the
  legacy stage list (14 for an app, 13 for an AAB).
- Scalar config values (SDK levels, variant, flags) need no
  per-task declaration: they are all inside `project-model`.

Every builder `SOURCE` input is required. That is not an
oversight: config load already rejects a missing declared path
(see the CCB-E1015 analysis below), so an optional declaration
would be a lie. Optional inputs exist only in hand-built graphs.

## Validation

*ccb-graph-validation*

`ccb_graph_validate` reports every problem it finds:

| Code | Meaning |
| ---- | ------- |
| CCB-E1012 | Duplicate task ID. |
| CCB-E1013 | Invalid task-graph reference: unknown dependency; GENERATED input produced by no task, produced by the task itself, or produced by a task the consumer does not depend on (directly or transitively); two tasks claiming the same output; a dependency, input, or output declared twice on one task; one input declared with conflicting kinds; a SOURCE input that is also the task's own output. |
| CCB-E1014 | Task dependency cycle, naming the cycle path (e.g. `a -> c -> b -> a`), following the CCB-E1010 module-cycle pattern. |
| CCB-E1015 | Missing required SOURCE input file (reported by `ccb_graph_check_source_inputs`, which the pipeline does not run — see below). |

The producer-dependency and cycle checks run only when every
earlier check passes; a graph with an unknown dependency reports
that instead. The producer rule is what closes audit finding C8
(config load was the only graph validation): dependencies are the
graph's only ordering, so a consumer of a GENERATED input must
depend on its producer, directly or transitively — otherwise the
plan could run the consumer before the artifact exists. The
pipeline satisfies this through its linear chain: `package`
consumes `linked-apk` from `link` without a direct edge, but
`link` is a transitive dependency, so it validates. A dependency
with no shared input is legal (ordering-only, e.g. `native` after
`dexcheck`), and an output no task consumes is legal (a final
artifact, e.g. `signed-artifact` is consumed by `verify`, but
`library-aar` is the product itself).

The pipeline builder declares each SOURCE input once: config lists
may repeat a path (the same AAR twice, a `java_extra` dir equal to
the java dir) and the engine would reject the duplicate. The
engine stays strict for hand-built graphs.

Determinism: planning is a pure function of the graph — Kahn
topological order with insertion order breaking ties. Planning the
same graph twice, or rebuilding it identically, yields the
identical plan; this is pinned by tests, including a 51-task
layered graph.

Deliberately not wired in: `ccb_graph_check_source_inputs`
(E1015) is still not run by the pipeline, and the per-input
required/optional analysis behind that decision is now complete:

- Every `SOURCE` input the builder declares is already
  existence-checked before the graph is built: config load
  (`ccb_check_paths`) rejects a missing manifest, res, assets,
  kotlin/java/java_extra dir, `CMakeLists.txt`, libs dir, SDK or
  Kotlin home, R8 jar, ProGuard rules, keystore, jar, AAR, or NDK
  source with CCB-E1005/CCB-E1006, and module/library dirs are
  checked the same way. A pipeline pre-check could never fire
  for those inputs — the build is already dead with a more
  specific code.
- The paths the steps read that the builder does *not* declare
  are resolved in stage 0, before the graph exists: Maven AARs /
  jars and compiler plugin jars come from the Maven cache, and a
  cache miss fails stage 0 with its own code.
- The genuinely optional inputs stay undeclared for a reason:
  `assets` is declared only when configured (and then
  load-checked), and the default debug keystore is generated by
  the sign step when absent — failing the build for its absence
  would break every first debug build.
- The remaining case, a *required* file that exists at load and
  disappears before its step runs, is a race no pre-check can
  close; the step's own diagnostic is the right one there.

So wiring E1015 into `ccb_pipeline_build` would only mask
step-specific codes or duplicate config load, never add a
diagnosis. The check stays an engine API for hand-built graphs
(where the caller decides which inputs are required), with the
required/optional flag in the input model so a later step can
wire it in if a pipeline input ever becomes genuinely optional.
Likewise no `ccb graph --check-inputs` flag was added: it could
never fire on a pipeline graph, because config load fails first.

## Execution

*ccb-graph-execution*

The executor is sequential: it repeatedly marks `WAITING` tasks
whose dependencies are all `DONE` as `READY`, runs the first ready
task, and repeats. On the first failure the failing task is marked
`FAILED`, every task that has not run is marked `CANCELLED`, and the
failing status is returned. Diagnostics added during the failed task
gain its task ID. A task that skips on a cache hit sets its
`skipped` flag; the executor records `duration_ms` per task.

## Parallel execution (Step 8)

*ccb-graph-parallel*

`src/ccb_sched.{h,c}` is a parallel executor for the same graph: a
pthread worker pool, a centralized ready queue (FIFO, insertion
order among tasks that become ready together), per-task
pending-dependency counters, and a configurable worker count
(`ccb_graph_execute_parallel(g, ctx, log, diags, workers)`; 1
worker behaves like the sequential executor). Failure propagation
and cancellation match the sequential semantics: the first
failure's status is returned, `WAITING`/`READY` tasks become
`CANCELLED` and never start, and a task already `RUNNING` when
another task fails runs to completion (no preemption). The
scheduler object (`ccb_sched_create` / `ccb_sched_cancel` /
`ccb_sched_run`) also lets another thread cancel a running build.
`workers == 0` is CCB-E1016. There is no work stealing, no
distributed scheduling, no priorities, and no CLI flag or config
option: parallel execution of real builds is OFF, and no build
path calls the parallel executor yet.

That last point is deliberate, not an oversight. A run function
executed in parallel must own every piece of state it mutates; it
must not write the shared `ccb_log` (not even `ccb_log_cache` —
the log's `last_cache_reason` stash is shared), the shared
`ccb_diag_list`, the shared `ccb_cache`, or the pipeline pipe.
Real pipeline steps still share all four, so they are not safe to
run concurrently. What Step 8 closed instead, so a later step can
wire real tasks in:

- Per-task artifact ownership: a module build fills a
  task-owned `ccb_mod_artifact` (AAR path, classes jar, manifest
  source, res/assets dirs, package) and never touches the pipe's
  shared AAR lists; the driver merges it with
  `ccb_mod_register_artifact`, in topological order, from the
  single driver thread.
- Single-writer cache publication: a completed task records its
  step fingerprint in a task-owned `ccb_cache_delta`; the driver
  merges it into the shared cache after the task succeeds, and a
  failed task's delta is discarded with the task, so a failed step
  never publishes a cache entry. The cache file itself is
  published at most once per build, atomically (temp file +
  rename), from the driver thread only, and only when something
  changed (`cache_dirty` — a no-op build leaves the file
  untouched). A failed build still saves the completed steps'
  deltas, so a retry resumes them.
- Per-module graph tasks (above): the fan-out unit exists in the
  graph, with per-module dependency edges and per-task outputs.

Proven stages (`tests/test_sched.c`, deterministic — barriers and
condvar gates, no sleeps, no timing assertions): stage 1
(single-worker execution matches the sequential executor's order
and states; cycles and zero workers fail before any thread
spawns), stage 2 (two independent tasks provably concurrent),
stage 3 (dependency gating, failure propagation at 1 and 4
workers), stage 4 (cancellation mid-run and before run, 64-task
stress at 4 workers), stage 5 (cache deltas: invisible until
merged, later merge wins, failed delta discarded). Stage 6 —
parallel execution of real build tasks, with sequential-vs-parallel
byte-identical APK equivalence — is NOT reached: it needs
per-task diag/log/cache/pipe state first. Two known parallel-mode
limits follow from the shared state above: a skipped task's
`skip_reason` is `null` (the sequential executor reads it from
the shared log stash), and diagnostics a failed task adds are not
stamped with its task ID.

## Inspecting the plan

*ccb-graph-plan*

`ccb build --explain` prints the plan first, then the per-step
run/skip lines as before:

```c
build plan (14 tasks, in execution order):
  config
  deps (after: config)
  libraries (after: deps)
  ...
  verify (after: sign)
```

`ccb graph [--aab]` prints the same plan without building anything
(human table by default; one `build_plan` JSON object with
`--json`). In JSON each input is an object with its `name`, `kind`
(`source`, `generated`, or `env`), and `required` flag — the kind
and optionality are part of the plan, not just the name. It loads
the config read-only and resolves no toolchain, so it works
without an SDK installed. `--aab` shows the AAB plan
(`package-aab` instead of `package`, no `align`).

Affected tasks — which tasks a changed input invalidates — are
computed by `ccb_graph_affected`: a task is affected when one of its
inputs names a changed input, or when it transitively depends on an
affected task. `ccb graph --affected INPUT` exposes it: a human list
in execution order, or one `affected` JSON object with `--json`.
The input is matched by declared name — a file path, a logical
name such as `dex` or `toolchain`, or an environment variable
name. A relative file path is resolved against the project root,
because declared paths are project-root-resolved absolute paths.
This is the graph primitive Phase 3 (incremental cache) and Phase 5
(multi-module) build on.

## Build summary and task events

*ccb-graph-summary*

In `--json` mode each task emits lifecycle events:

```json
{"event":"task","task":"compile-code","status":"started"}
{"event":"task","task":"compile-code","status":"finished","duration_ms":5211,"result":"done"}
{"event":"task","task":"compile-res","status":"finished","duration_ms":12,"result":"skipped","reason":"resource inputs unchanged"}
```

`result` is `done`, `skipped`, or `failed`. A skipped task carries
its `reason` (absent when the skip logged no reason). Human mode
stays unchanged: phase lines already show progress.

The final `build_done` object gains a `tasks` array, one object per
task in plan order:

```json
{"event":"build_done","apk":"build/outputs/debug/app.apk","steps_run":2,"steps_skipped":8,"up_to_date":false,"tasks":[{"id":"config","state":"done","duration_ms":41,"skipped":false,"skip_reason":null}, …]}
```

Each object is `{id, state, duration_ms, skipped, skip_reason}`;
`skip_reason` is the reason string for a skipped task, else
`null`.

Tasks that never run (cancelled after a failure) report
`duration_ms: -1`. On a failed build the same array goes out as a
standalone `{"event":"build_summary","tasks":[...]}` object before
the diagnostics. Diagnostics from a failed task carry its ID as
`"task"` in JSON and `[task <id>]` in human output.

## Equivalence proof

*ccb-graph-equivalence*

The graph-driven build is proven equivalent to the old driver by:

1. `tests/test_graph.c`: the pipeline graph's topological order
   equals the legacy stage order exactly (app, AAB, and library
   graphs).
2. A real `examples/hello` build before and after the change:
   identical `--explain` run/skip lines and byte-identical APKs
   (reproducible builds: fixed timestamps, deterministic order).
   Baseline (pre-change binary): APK
   `9736bbae9c5bfdad383418d96ba8dddf6a10a96a68e7e3ffa809031e42ff5c3f`;
   the graph-driven build reproduces the same hash.

## What Phase 1 deliberately does not do

*ccb-graph-not-done*

- No parallel real builds: the parallel executor exists (Step 8,
  above) but no build path calls it — real steps still share one
  log, one diag list, one cache, and one pipe.
- No new cache design: skip decisions are still the steps' own
  fingerprint comparisons (Phase 3).
- No provider extraction: Android stages are still `ccb_step_*`
  functions wrapped as tasks (Phase 4).
- No `ccb_pipe` redesign: the god-struct stays the shared context
  the steps read; splitting it is a Phase 4 concern
  (see [architecture audit](architecture-audit.md)).
- No module ID on diagnostics: tasks carry IDs; module IDs arrive
  with the multi-module model (Phase 5).
